## 1. 改了什麼

#257 的評測發現：模型觸發模式下，助理同時有表單與可提議的案件類型時，獨立的表單選擇呼叫會先接走所有該開案的題目（整條提議階段漏觸 16/16）。負責人 2026-10-07 決定採用決定 L 的替代方案：

- **合成呼叫**（`ProposalSelectionRules`、`ChatProposalSelectionTool`）：同一則請求同時可以提供表單與至少一個案件類型時，只呼叫一次模型，同時提供 `request_database_form` 與 `propose_case`（兩個工具定義都沒有改），模型最多選一個，或都不選。
  - 只有表單、或只有案件類型時，維持原本的單一呼叫，行為不變。
  - 優先順序照舊：數據庫查詢 → 表單 → 案件 → 一般回答，每則回覆最多一個提議。提示寫明「兩者都同樣符合時，用表單」；模型失敗時先看表單關鍵字、再看案件關鍵字。
  - 伺服器只接受列出的表單 id 或類型 id，表單會依那個 id 重新授權。
- **用途**：新增 `ModelInvocationPurpose.ProposalSelection`（`proposal-selection`），計入每月 token 用量（`OrganizationTokenUsageRules.CountedPurposes`）。
  - 不沿用 `form-request` 或 `case-proposal`，因為這一次呼叫同時決定兩件事，用任一個名稱都會誤報。
  - 單一工具的呼叫仍是原本的用途。
- **`smartagri.form-check`**：名稱、值、位置都不變。合成呼叫也提供表單，所以在同一個位置送出一次；只有案件的呼叫仍然不送。前端顯示的是通用的「助理正在整理你的問題」，收到第一段文字或回覆就結束，案件提議也是先送文字，所以前端不用改。
- **案件選擇提示的邊界**（`CaseProposalRules.SelectionBoundaries`，單一案件呼叫與合成呼叫都套用）：
  - 以下情況不要提議：詢問既有案件或申請的進度、取消已送出的申請、詢問統計數字、只是抱怨或陳述而沒有要求處理。
  - 不屬於任何類型的事（例如作物病蟲害），不要套用最接近的類型。
- **評測 CLI**：
  - `eval-case-proposals`：模型的「整條提議階段」改走合成呼叫，與正式環境相同。「只看案件層」仍是只提供案件工具的單一呼叫，也就是助理沒有表單時的正式路徑。
  - `eval-form-requests`：新增 `--case-types <題庫目錄>`，每題另外做一次合成呼叫（表單工具＋案件題庫的三個類型），檢查表單題會不會被案件搶走。

## 5. 如何重跑

```sh
# Development 環境；不需要資料庫。金鑰只放在環境變數，不要寫進檔案或報告。
export Ai__Chat__Provider=OpenAI
export Ai__Chat__Model=gpt-6-luna
export Ai__Chat__ApiKey=<金鑰>
export Ai__Chat__ReasoningEffort=None     # gpt-6-luna 必須，否則工具呼叫回 HTTP 400
dotnet run --project apps/api/src/SmartAgri.Api -- eval-case-proposals --report "$PWD/docs/evals/<日期>-case-proposals-<模型>.md"
dotnet run --project apps/api/src/SmartAgri.Api -- eval-form-requests --case-types "$PWD/apps/api/eval/case-proposals" --report "$PWD/docs/evals/<日期>-form-requests-<模型>.md"
```

兩個 CLI 的預設報告檔名不含票號，同一天重跑會覆寫既有報告，所以請指定 `--report`。
