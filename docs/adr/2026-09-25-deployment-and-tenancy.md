# ADR｜部署型態、組織隔離與客製方式

**狀態：** 已確認（2026-09-25）

## 決策

- **產品定位**：後端核心是通用的 AI 助理平台，農業是主要客群之一而非核心模型。農業特有資料（例如感測器）以數據庫來源或助理可呼叫的工具接入，不寫進核心領域。
- **部署型態**：同一份程式碼同時支援「單一組織部署在客戶自己的雲端或機房」與「我方營運的多組織 SaaS」；設計以前者為主要目標，不依賴任何只有特定雲才有的託管服務。
- **組織隔離**：從第一版起，所有業務資料都帶 `OrganizationId`，每一次查詢都由服務端依目前帳號所屬組織過濾；即使部署時只有一個組織也一樣。
- **客製方式**：客製由我方以外掛點實作，或由客戶在後台以設定組裝（助理、規則、資料來源、發布管道）。不交付原始碼給客戶或其 SI 夥伴。

## 理由

「客製」的客戶多半會要求部署在自己的環境，但我方也需要一套 SaaS 服務中小型客戶。事後才替既有資料補上組織欄位並改寫所有查詢，成本遠高於一開始就帶著；前端原本沒有組織概念，只有隱含的「公司」；此決策把它定為「組織」，畫面用語一併改為「組織」（見 `docs/glossary.md`）。

不交付原始碼，第三方授權審查可維持在「可商用、可修改、可閉源散布」的寬鬆授權範圍；若改為交付原始碼，需重新審查所有依賴。

## 影響

- 帳號、助理、草稿、知識庫、數據庫、對話、發布設定的資料表都需要 `OrganizationId`，並有防止漏過濾的機制（例如 EF Core 全域查詢篩選）與對應測試。
- 找不到資源與無權限都回相同的 403，避免跨組織探測（沿用 `docs/handoff/tasks-6-10-backend-handoff.md` 的規則）。
