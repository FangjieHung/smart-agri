## 整體判斷

目前前端已串起助理建立與設定、知識來源、對話、同意提交、發布管道及團隊設定等操作流程。後端 M1 已建立登入、組織隔離、`/me` 與團隊權限；API 模式只有團隊功能接上真實後端，其餘業務功能仍使用瀏覽器內的 `MockDemoRepository`。這符合 [M1 範圍](../plans/2026-09-25-backend-milestone-1-skeleton.md)，但 API 模式不能當成完整業務系統交付。

既定的後端建置順序為「骨架 → 知識庫 → 有引用的平台內對話 → 數據庫 → 對外發布」，應依 [里程碑 ADR](../adr/2026-09-25-milestone-order.md) 推進。現有後端的組織查詢篩選與寫入保護是良好的基礎；以下資料碰撞指的是前端 **mock 儲存**，不是已證實的後端資料庫跨組織漏洞。

## 以公司實際操作流程檢視

本檢視涵蓋三個要落地的場景：**內部知識**、**客服**、**跨部門通用流程**。現有 Demo 的商行客服、商品指南、退換貨政策與配送 FAQ 是已可對照的例子；跨部門情境則以採購、營運、業務、財務與人資共用 SOP、表單與交接紀錄為驗收基準。這是業務流程審查，不表示下列功能已開發。

### 三個業務場景的目標與差異

| 場景 | 使用者要完成的工作 | 主要資料 | 上線前必須驗證 | 特有缺口 |
| --- | --- | --- | --- | --- |
| 內部知識 | 新同仁查 SOP、商品規格、作業規則；資深同仁快速找到正確版本。 | SOP、教育訓練教材、規格書、制度辦法、內部 FAQ。 | 回答能引用有效版本與頁碼／章節；無權限內容不可被檢索或顯示。 | 文件責任人、版本生效日、覆核與知識交接。 |
| 客服 | 回答商品、配送、退換貨問題；遇到個案時引導客戶留下資料並交由人工處理。 | 商品資料、退換貨與配送政策、對外 FAQ、訂單與客訴表單。 | 一般政策與個案資料清楚分開；查無答案或高風險問題能轉人工；對外答案不可引用舊政策。 | 服務水準、案件分派、人工回覆閉環、公開前審核與回滾。 |
| 跨部門通用流程 | 將流程知識、申請表單與交接事項串起來，例如採購申請、庫存異常、報價、請款、人員到職。 | 部門 SOP、表單、流程規則、角色權限、受控結構化紀錄。 | 每一步知道負責人、目前狀態與下一步；部門間只看得到被授權的內容與紀錄。 | 工作項目／案件狀態、指派與交接、時限提醒、跨部門存取與稽核。 |

跨部門需求不能只把更多 PDF 丟進同一知識庫。文件回答「怎麼做」，表單記錄「發生了什麼」，工作項目則管理「接下來誰要做」。三者要分開建模，再由助理依權限串接；否則聊天可以回答流程，卻無法承接真正的交辦與追蹤。

| 業務步驟 | 實際操作與責任人 | 目前可做到 | 待補缺口與業務後果 |
| --- | --- | --- | --- |
| 盤點與分工 | 管理者指定商品、客服、物流等內容負責人，決定每類文件給哪些助理及對象使用。 | 可設定知識庫分享範圍、連接助理；團隊權限可調整。 | 無成員新增、內容負責人、覆核人及更新週期；文件過期時難以找到負責者。 |
| 建立來源 | 負責人按用途建立知識庫，區分商品說明、有效政策、內部 SOP、對外 FAQ。 | 清單只顯示既有 seed；空狀態沒有建立入口。 | 空組織不能從零導入自己的資料。 |
| 收件與批次匯入 | 一次選取整批文件，確認格式、數量、大小、重複檔與上傳結果；失敗項可單獨重試。 | 詳情頁只有「加入示範文件」，不讀取檔案。 | 真實資料無法進系統；幾十份文件逐一處理會耗費人力。 |
| 整理有效版本 | 將文件批次分類、標記適用對象與生效日期，找出舊版、重複與互相衝突的內容。 | 文件只有名稱、狀態、錯誤與更新時間；沒有批次操作。 | 舊退貨政策與新版同時被檢索時，助理可能引用錯誤版本。 |
| 解析與校對 | 檢查每頁、章節或工作表抽出的文字和表格；掃描頁、加密檔及漏讀欄位交給人處理。 | 有等待、處理、可使用、部分可讀、失敗五種狀態，進度由前端計時器模擬。 | 「可使用」無法證明內容被正確讀取；錯誤可能直到回答時才被發現。 |
| 轉成可用知識 | 保留標題層級、表格欄位與單位、來源位置、有效日期及存取範圍，產生可檢索段落與經覆核的 FAQ。 | 文件模型沒有抽取內容、段落預覽、版本或核准狀態；試問使用固定範例回答。 | 上傳完成與「能正確回答」之間缺少可驗證的轉換步驟。 |
| 試問與上線 | 客服主管用常見、邊界及應拒答問題驗收，確認引用、權限與更新版本後才讓助理使用。 | 精靈有模擬試問；正式檢索與引用驗證尚未實作。 | 不能以業務答案品質作發布門檻。 |
| 日常維護 | 政策變更時替換版本、讓受影響助理重建索引、回歸測試；處理查無資料與錯誤引用。 | 可看文件狀態與連接助理；沒有替換、停用、差異、回滾或品質工作清單。 | 內容會逐漸過期，且不易知道哪些助理受影響。 |

### 一批文件實際導入時，使用者應看見什麼

例如客服主管要導入商品指南、退換貨辦法與配送時間表。系統應先列出本次選取的檔案與檢查結果，讓他把新版退貨政策標為生效版本，將舊版封存；加密 PDF 提示解除密碼，掃描頁提示目前無法擷取文字，Excel 顯示辨識出的工作表、欄名和單位。完成解析後，主管應能預覽「收到商品幾天內可退貨？」會引用哪一版文件、哪一頁；如果兩份政策答案衝突，應先指派負責人處理，不能只因處理狀態是 `ready` 就自動供對外助理使用。

可供系統有效利用的資訊，至少要保留**原檔、可讀內容、來源位置、文件版本、適用範圍與權限**的關係。依已確認的 [知識來源 ADR](../adr/2026-09-25-assistant-access-to-knowledge-and-databases.md)，第一版接收有文字層的 PDF、DOCX、XLSX、純文字／Markdown 與 FAQ；不做 OCR，掃描頁需明確標示不可讀。依 [可信回答 ADR](../adr/2026-09-25-grounded-answers.md)，組織資料的回答需驗證引用來自本次檢索，查無足夠資料時不呼叫模型。

### 建議的交付切法

只做「多檔上傳後自動切段」最快，但無法回答哪一版有效、內容是否漏讀。一次建完整文件管理平台則會延後驗證核心價值。較合適的第一個業務閉環是：**建立知識庫 → 批次上傳一組有文字層的文件 → 顯示抽取預覽與逐檔結果 → 人工確認有效版本 → 用真實檢索試問並核對引用 → 開放內部助理使用**。批次標籤、進階衝突偵測、排程提醒與 OCR 可依使用量往後擴充。

### 知識庫之外，仍需接上的業務環節

| 環節 | 待補的業務決定或功能 | 建議時點 |
| --- | --- | --- |
| 組織成員生命週期 | 新增成員只是第一步；還要定義停用、離職、職務異動後誰接管其知識庫、助理與待審事項，以及既有分享何時失效。 | 多人正式使用前 |
| 問題未解決時的處理 | 客戶問不到答案、引用有疑義或需要查個別訂單時，應能給明確下一步並交由指定人處理；不能只回「查無資料」後結束。是否串接既有客服系統需另定。 | 平台內真實對話完成後、對外發布前 |
| 結構化紀錄 | 訂單、客戶回報等資料須走受控查詢與表單，不應塞進文件當作即時資料；需明確定義紀錄更正、重複提交、同意撤回後報表如何更新。 | 數據庫里程碑 |

## 待補功能

### 1. 新增組織內成員帳號

**目標：** 具有團隊管理權限的帳號能在目前組織內新增成員，讓成員以自己的真實帳號登入，並在團隊設定中管理其角色與權限。不得把新成員映射成既有的三個 Demo 身分之一。

**實作前置條件：**

1. 將團隊 API 與畫面的成員識別值統一為真實帳號 ID，先解決同角色成員會互相覆蓋、編輯錯人的問題。
2. 確定 API 模式仍屬 mock 的草稿、對話及其他業務資料如何依組織與帳號隔離；在隔離完成前，不能讓新增成員誤用共用的模擬資料。
3. 定義建立者權限、初始角色與權限、登入名稱在組織內唯一的驗證，以及首次登入設定密碼的方式。現有 `setup` 一次性密碼流程可作參考，但新增成員流程尚未設計完成。

**預期驗收：**

- 只有具備適當團隊管理權限的帳號能新增；其他帳號看不到成員資料，也不能直接呼叫 API 新增。
- 新成員只屬於目前組織；相同登入名稱在同組織內被拒絕，在不同組織可分別存在。
- 同一組織可新增多位相同角色的成員；團隊清單各列有不同 ID，修改 A 的權限不會修改 B。
- 新成員可以完成首次登入與必要的密碼設定；失敗時有明確的驗證及復原訊息。
- 至少有 API 整合測試覆蓋授權、跨組織隔離、同角色多人、重複登入名稱，以及前端端到端測試覆蓋新增後登入與權限修改。

此功能在既有 [M1 計畫](../plans/2026-09-25-backend-milestone-1-skeleton.md) 中明列為範圍外；新增前需先解決上面的身分橋接與資料隔離門檻。

### 2. 建立知識庫與批次上傳文件

**目標：** 新組織不用依靠 seed 資料，就能建立知識庫並一次導入多份實際文件。

**預期驗收：** 可建立並命名知識庫、指派負責人；批次選檔後顯示每檔的格式、大小、重複與上傳結果；個別失敗可重試而不重傳整批；一批完成後可清楚區分成功、部分可讀與失敗。背景處理接續已確認的 [PostgreSQL 佇列 ADR](../adr/2026-09-25-background-jobs-on-postgresql.md)，前端不再用計時器假造進度。

### 3. 文件批次整理、版本與生效管理

**目標：** 讓業務負責人能在上線前確認「哪些內容是目前有效的」，而不只看檔案是否解析成功。

**預期驗收：** 可批次移至知識庫、標記類別與適用對象；辨識完全相同檔案並提示可能的新版／舊版；同一文件可上傳新版本、設定生效日期、封存舊版與緊急停用。替換版本時顯示受影響的助理；新版本未核准前，舊有效版依既定規則維持使用，緊急停用則立即停止新回答引用。版本與操作人可追溯。

### 4. 文件內容轉換、預覽與人工校對

**目標：** 讓負責人確認系統實際讀到的內容，並把它整理成能被檢索與正確引用的知識。

**預期驗收：** 可按頁、章節或工作表預覽抽取內容，顯示漏讀頁、加密錯誤與表格欄位問題；可排除不應檢索的封面、附錄或舊條款。每個可用段落保留原檔版本與頁碼／章節／原文位置，並套用組織、知識庫、文件及使用對象的權限。常見問答可由文件整理成草稿，但須由人確認答案與來源後才啟用。第一版不把掃描影像誤標為已讀取。

### 5. 真實試問驗收與持續維護

**目標：** 將「處理完成」與「業務可上線」分開，由內容負責人驗證答案後發布，並在政策更新時持續維護。

**預期驗收：** 每個助理有一組可保存的常見、例外、應拒答測試題；試問顯示檢索段落、來源版本與引用，答錯或查無結果可建立處理事項並指派負責人。文件改版或權限變更後，受影響助理的題組需重跑；未通過時保留內部使用或阻止對外發布。營運指標至少能看到文件處理失敗、過期待審、查無資料及錯誤引用的趨勢，且不揭露使用者私人對話內容。

### 6. 跨部門案件、交接與追蹤流程

**目標：** 讓助理不只回答 SOP，也能把「需要做事」的問題轉成有負責人、狀態與時限的受控工作項目；適用於訂單異常、採購申請、報價、請款、庫存異常與人員到職等流程。

**預期驗收：** 使用者能從助理答案或表單建立案件，選擇流程類型、必要欄位、負責部門與處理時限；案件有草稿、待受理、處理中、待補件、已完成與已取消等可追蹤狀態，交接時保留操作人與時間。每位成員只看得到被指派或被授權的案件與附件；知識庫權限、結構化紀錄權限與案件可見性分別判斷。助理只能依既定規則建議下一步，不能自行變更付款、核准或人事等高影響決策。逾期、退回或資料不足時要通知負責人，並能由管理者檢視不含私人對話全文的流程瓶頸。
