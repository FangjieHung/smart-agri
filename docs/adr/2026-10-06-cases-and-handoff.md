# ADR｜跨部門案件、交接與追蹤

**狀態：** 已確認（2026-10-06，負責人決定）

## 背景

[業務流程審查](../reviews/2026-09-26-project-review-and-backlog.md)的待補功能 6，要讓助理不只回答 SOP，也能把「需要做事」的問題變成有人負責、有狀態、有時限的工作。[里程碑 ADR](2026-09-25-milestone-order.md) 留下兩個問題給這份 ADR：案件與處理事項（`AssistantIssue`）是不是同一個概念，以及案件排在哪個里程碑。

本 ADR 回答這兩個問題，並定下第一版的範圍。用語以 [`docs/glossary.md`](../glossary.md) 為準：案件、承辦組、案件類型、處理事項、轉給專人。

## 決策

### 里程碑

案件排在 **M7**：M5b LINE 之後是 M6 組織設定，再來是 M7 案件。

### 案件與處理事項是兩個概念

- **處理事項**：助理本身需要修正。由維護助理的人處理；結案表示助理已修好。
- **案件**：業務上「接下來誰要做」。由承辦組處理；結案表示事情已辦完，與助理答得好不好無關。
- 兩者不合併，`AssistantIssue` 也不遷移。
- 兩者之間不能互相轉換。維護助理的人在處理事項上可以「另開案件」：
  - 新案件預先帶入處理事項的問題摘要；
  - 案件與處理事項互相連結；
  - 處理事項以「非助理問題」結案。

### 承辦組，不建部門

- 不建立「部門」資料。改用**承辦組**：組織自行定義、可受理某類案件的一群帳號，不必對應組織架構。
- 承辦組由管理者建立並加入成員。管理者以角色（`smb-admin`）判斷，不是某一項權限（M6 計畫決定 A）。
- 是承辦組成員，就能受理該組的案件。不新增權限。

### 案件類型

- 案件類型由管理者定義。每個類型有：
  - 預設承辦組；
  - 預設處理時限；
  - 說明（助理提議開案時，靠它判斷該用哪一類）。
- 建立案件時先選類型。承辦組與處理時限依類型預先帶入，可以修改。
- 統計以類型為單位。

### 案件內容

- 案件有標題、說明，以及對既有資料的連結（一筆數據庫紀錄、一個對話串）。
- 不依類型自訂欄位。需要結構化資料時，用 M4 的表單與數據庫。

### 案件從哪裡來（第一版）

1. **平台內手動建立**：組織內部帳號直接建立。
2. **助理在對話中提議，使用者確認後建立**：與 M4 請填表單的流程相同。
3. **數據庫紀錄送出後自動建立**。

訪客（官網、LINE）建立案件延後。它需要訪客的身分與聯絡方式，也就是個資；M5a 對訪客什麼都不保存。

### 助理提議開案

- 每個助理有「可提議的案件類型」，預設為空。授權方式與「助理可連結哪些數據庫」相同。
- 何時提議，沿用表單請求的觸發方式設定（關鍵字／模型）。
- 從對話建立的案件，只保存使用者確認過的標題與說明，再加上對話串的連結。不複製對話內容；這點與處理事項保存問答副本不同。
- 對話串之後若因保存期限被刪除，連結只是變成無法開啟。

### 助理不能改變案件狀態

- 助理只能提議建立案件。所有狀態變更都由人操作。
- 「助理不可決定付款、核准、人事」就靠這條規則落實：這類決定一定落在某個由人改變狀態的案件上。

### 數據庫送出後自動開案

- 由管理者在數據庫上設定：「送出後自動開某類型案件」。
- 案件連結到那筆紀錄。
- 案件沒有建立者。送出者不因此看得到案件。
- 不把紀錄內容複製到案件。送出者可能是外部客戶；複製了，撤回就形同失效。
- 設定畫面提示承辦組中有幾位成員無法讀取這個數據庫的紀錄。
- 以上見 M7 計畫決定 M（2026-10-06）。
- 紀錄之後若被撤回，案件保留，連結顯示「紀錄已撤回」。

### 狀態與流轉

狀態只有五個：**待受理、處理中、待補件、已完成、已取消**。

| 動作 | 誰可以做 | 結果 |
| --- | --- | --- |
| 受理 | 案件所屬承辦組的成員 | 成為案件負責人，狀態由待受理變處理中 |
| 待補件 | 只有案件負責人 | 狀態變待補件；建立者回覆補充資料後，自動回到處理中 |
| 繼續處理 | 只有案件負責人 | 狀態由待補件回到處理中（例如對方用電話補件） |
| 完成 | 只有案件負責人，必須填處理結果 | 狀態變已完成 |
| 取消 | 受理前：建立者（原因選填）或管理者（必須填原因）。受理後：案件負責人或管理者，必須填原因 | 狀態變已取消 |
| 轉組 | 案件負責人或管理者 | 改到另一個承辦組，回到待受理，清空案件負責人 |

（2026-10-06 補充：繼續處理與管理者受理前取消，見 M7 計畫決定 J）

- 每一次交接（受理、轉組）都記下誰、何時，成為交接軌跡。
- 已完成的案件不能重新開啟。要繼續處理時「另開新案」，並連結舊案件。

### 處理時限

- 第一版在待補件期間不暫停計時。
- 案件負責人可以調整時限，每次調整都留紀錄。

### 逾期通知

- 只在平台內通知，不寄 Email。
- 逾期在讀取時依處理時限判斷，以側欄數字、首頁卡片與清單篩選呈現；不另建通知資料，也不排每日作業（M7 計畫決定 D）。
- 有案件負責人時通知負責人；還在待受理時，通知該承辦組的所有成員。
- 管理者從瓶頸統計看到逾期，不另外通知。

### 誰看得到案件

案件可見性單獨判斷，不沿用知識庫或數據庫的權限。看得到的人：

- 建立者；
- 目前承辦組的成員；
- 曾經擔任這個案件負責人的人；
- 管理者。

轉組之後，原承辦組的成員就看不到了，除非他曾是案件負責人。例如：「冷藏庫溫度異常」先由設備組受理，再轉給採購組。設備組的阿明如果曾受理這件案件，轉組後仍看得到；如果只是設備組成員、沒受理過，轉組後就看不到。

### 瓶頸統計

- 管理者可以依案件類型與承辦組，看到件數、逾期件數與平均處理時間，也能點開個別案件。
- 案件本身永遠不含對話文字，只有對話串的連結；能不能開啟那個對話，由對話本身的權限決定。

### 第一版只給組織內部帳號

- 外部客戶建立、追蹤自己的案件延後。它需要先設計「哪些欄位對外可見」，才不會讓內部備註外流。
- `read-own-tracking` 權限維持不接行為。

### 保存

- 案件永久保存，與定期報表一致。
- 案件不受對話保存期限影響，因為它只存摘要，不存對話內容。
- 系統目前沒有刪除或停用帳號的功能。找不到帳號名稱時，一律顯示「已停用的帳號」，與其他畫面一致；案件對帳號的參照不得因帳號異動而遺失（2026-10-06 修正，原寫「建立者的帳號被刪除後，顯示為『已刪除的帳號』」）。

## 理由

處理事項與案件的處理人、權限、結案條件與統計方式都不同。合在一起，同一個詞就要指兩件事，統計也會混在一起；分開之後，兩邊的狀態機都能保持簡單。

不建部門，是因為能受理某類案件的人常常跨部門，也常常只是部門裡的幾個人。承辦組直接表達「誰能接這類案件」，不必先建一套組織架構。

不保留審查文件中的「草稿」狀態：助理提議的內容在使用者確認前只存在對話裡；手動建立是直接送出；而「草稿」在用語表裡已經是「尚未完成的助理設定」。

不能重新開啟已完成的案件，是因為重開會讓完成件數與處理時間失真。另開新案並連結舊案，統計仍然正確，歷史也追得到。

逾期只做站內通知：部署沒有郵件設施，M4 的定期報表也只在站內查看。

## 考慮過的選項

- **把 `AssistantIssue` 併入通用的工作項目**：不採用。處理人、權限、結案條件與統計都不同，一個詞會有兩個意思。
- **處理事項與案件互相轉換**：不採用。改為「另開案件」並互相連結，兩邊各自結案。
- **依案件類型自訂欄位**：不採用。那等於第二套表單系統；結構化資料交給 M4 的表單與數據庫。
- **待補件時自動暫停處理時限**：不採用。邊界情況多（多次往返、回覆不完整時要不要恢復計時），也難以向使用者解釋；改由案件負責人手動調整並留紀錄。
- **建立部門資料**：不採用，理由見上。

## 影響

- M7 的計畫要新增承辦組、案件類型、案件、交接軌跡，以及處理事項上的「另開案件」與「非助理問題」結案方式。
- 助理設定要新增「可提議的案件類型」；數據庫設定要新增「送出後自動開案」。
- 案件可見性是新的一條權限判斷，要有自己的測試，不能借用知識庫或數據庫的判斷。
- 訪客開案與外部客戶追蹤案件，各自需要另一份 ADR。
