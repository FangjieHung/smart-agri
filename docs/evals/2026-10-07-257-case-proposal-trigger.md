# #257 助理提議開案觸發方式評測：關鍵字 vs 模型選擇工具

> **狀態：已以真實模型評測（2026-10-07）。** 關鍵字與 `gpt-6-luna`（`ReasoningEffort=None`）的完整報告是同目錄的 `2026-10-07-case-proposals-gpt-6-luna.md`（CLI 產生，含逐題結果與每題 token）。本文件整理結果與建議。

## 1. 目的

M7-9（#254）讓對話在表單沒有成立時提議開案，觸發方式沿用 `Chat:FormRequests:Trigger`：

- **關鍵字**（決定 T）：問題含開案關鍵字（報修、維修、修理、叫修、申請、請款、退貨、派人、安排、開案、立案），**而且**問題含某個可提議類型的名稱，或助理只有一個可提議類型。
- **模型**：表單沒有成立時，再做一次 `propose_case` 選擇呼叫（用途 `case-proposal`），只接受列出的類型 id。

M7 計畫第 7 節技術風險 5 指出：誤觸會讓使用者一直看到開案卡片，漏觸則案件開不出來。本評測量化兩種觸發方式的**漏觸、誤觸、選錯類型**，並檢查決定 L 的優先順序（數據庫查詢 → 表單 → 案件）在實際模型下的效果。

## 2. 方法

- **題庫**：`apps/api/eval/case-proposals/questions.json`，50 題繁體中文、農業與中小企業情境。助理同時有一份表單與三個可提議的案件類型：
  - 表單「田間異常回報」：記錄田區病蟲害與作物生長異常，方便技術人員追蹤處理。
  - `repair`「設備報修」：農機、灌溉、溫室、冷藏庫等設備故障或損壞，需要派人到場維修。
  - `purchase`「採購申請」：購買肥料、農藥、資材或設備，需要主管核准後才能下單。
  - `return`「客戶退貨」：客戶收到的農產品有品質問題、數量不符或寄錯，要求退貨、換貨或退款。

  | 類別 | 題數 | 內容 |
  | --- | --- | --- |
  | `case`（應提議案件） | 16 | 報修 6、採購 5、退貨 5；多題刻意避開類型名稱與開案關鍵字（叫貨、換一盒、退貨款…） |
  | `none`（不應提議） | 15 | 知識問題、問類型的規則／流程／欄位、問進度、關鍵字用在別的事（申請補助、安排採收）、「不用開案」；其中 5 題問題裡有類型名稱 |
  | `form`（應給表單，不是案件） | 6 | 病蟲害與作物異常的回報 |
  | `query`（應走數據庫查詢） | 5 | 統計問題，其中 3 題含開案關鍵字或類型名稱 |
  | `ambiguous`（模糊題） | 8 | 只陳述故障、只有「報修」兩字、取消申請、抱怨但沒要求退換等；只報告「與標記一致」 |

- **CLI**：`eval-case-proposals`（apps/api/README.md「Evaluating case-proposal triggers」）。每題對每種觸發方式各判兩次：
  - **只看案件層**：假設前面各層都沒有成立時，案件層會不會提議、提議哪個類型。關鍵字＝`CaseProposalRules.KeywordProposal`；模型＝以正式環境相同的 `CaseProposalRules.Declaration`／`SelectionPrompt` 呼叫一次，用 `ParseCall` 判讀（只接受列出的類型 id，與 `ChatCaseProposalTool.SelectAsync` 相同）。
  - **整條提議階段（決定 L）**：
    - 查詢層：一律用 `DatabaseQueryTools.AsksForStatistics`（正式環境提供查詢工具的前置檢查）判定，**不呼叫查詢模型**。正式環境中，查詢模型若不呼叫工具，問題會繼續往下走到提議；這部分屬於 #149，不在本評測範圍。
    - 表單層：關鍵字＝`AssistantFormRequestRules.AsksForForm`；模型＝與 #164 相同的 `request_database_form` 選擇呼叫。
    - 然後才是案件層。
  - 模型模式每題固定呼叫表單與案件各一次（案件層才能單獨評測），所以 token 合計是正式環境的上限。
- **判定**：漏觸＝`case` 題沒有提議案件；誤觸＝`none`、`form`、`query` 題提議了案件；選錯類型＝`case` 題提議了別的類型（分母是有提議的 `case` 題）。模型呼叫失敗只計數、不判定（本次 0 次）。
- **限制**：題庫是為了找出關鍵字的弱點而寫的，比率不是實際使用時的比率；`case` 16 題，一題約 6.3 個百分點。模型只跑一次，沒有量測同一題多次呼叫的變異。

### 如何重跑

```sh
# 只評關鍵字：加 --trigger keyword
```

### 3.3 類型名稱本身含開案關鍵字（#254 已知誤觸）

三個類型的名稱都含開案關鍵字（設備**報修**、採購**申請**、客戶**退貨**），所以有三個以上類型時，關鍵字模式實際上等於「問題提到類型名稱」。

- 非案件題中提到類型名稱的有 8 題（n01、n02、n03、n13、n15、q02、q03、a07）：關鍵字在案件層**全部 8 題都提議**；整條提議階段扣掉被查詢層接走的 q02、q03，仍有 **6 題**（「採購申請要多久才會核准？」「設備報修的流程是什麼？」「客戶退貨的規定是收到後幾天內？」「採購申請表要填哪些欄位？」「客戶退貨後的蔬菜可以再賣嗎？」「我想取消剛剛的採購申請」）。
- 模型在案件層只提議 2 題（q03 統計題、a07 取消申請），整條提議階段 1 題（a07）。
- 關鍵字的 5 題「不應提議」誤觸全部來自這個原因。

### 3.5 觀察

**關鍵字**

- 漏觸集中在「沒有寫出類型名稱」：有三個類型時，「要報修」「派人來修」「幫我申請買」「要求退貨」都不會提議；16 題只命中 3 題（c04、c07、c14，問題裡直接寫了「設備報修」「採購申請」「客戶退貨」）。
- 誤觸全部是 3.3 的「問類型本身」：問時間、流程、規定、欄位。
- 選錯類型 0：命中時一定是寫出的那個名稱。

**模型：案件層本身很準，但在決定 L 的順序下完全到不了**

- 案件層單獨看：16 題全部提議、類型全對，包含沒有任何關鍵字的說法（叫貨、換一盒雞蛋、退一部分貨款）；問類型規則、問欄位的題目都正確地不提議；標題草稿簡潔可用（例如「冷藏庫溫度無法下降，安排師傅檢修」）。
- **但表單層先接走了所有應提議案件的題目**：`request_database_form` 對 16 題 `case` 題全部給了表單（曳引機發不動、要採購有機肥、客戶要求退貨也一樣），所以整條提議階段的漏觸是 16/16。只要助理同時有寫入對象（表單）與可提議的案件類型，模型模式就**永遠不會提議開案**。
- 表單層也對 3 題知識問題給了表單（n06「番茄葉子捲曲是什麼原因？」、n09「有機肥跟化學肥差在哪裡？」、n14「不用開案，告訴我怎麼自己修理滴灌管就好」），以及模糊題 a03（客戶抱怨芒果太酸）。#164 的評測（2026-10-05，同一模型、相同提示）中這類知識問題都沒有給表單，**這次的表單層行為可能是模型變動或抽樣變異**；本票只跑一次模型，沒有重跑 `eval-form-requests` 確認。
- 案件層在沒有表單時的誤觸：表單題 6/6 被當成案件（作物異常 → 「設備報修」5 題、「申請處理田間蚜蟲」→ 採購 1 題），問進度（n04「上次報修的冷氣修好了嗎？」）、統計題 q03、取消申請 a07、只是抱怨 a03 也被提議。也就是說，模型傾向「有事要人處理就開案」，不太看類型說明的邊界。
- 整條提議階段唯一的誤觸是 n04（問進度，表單層沒給、案件層提議了「冷氣設備報修」）。

## 4. 建議

1. **（最重要）先處理表單層吞掉案件的問題，再談切換觸發方式。** 部署預設已經是 `Model` 觸發（`deploy/docker-compose.yml`），所以只要助理同時連接寫入對象與可提議類型，正式環境就開不出案件。可選做法（請負責人決定，建議另開一張票）：
   - a. 採用決定 L 當時列的替代方案：助理同時有表單與案件類型時，**表單與案件放進同一次選擇呼叫，讓模型二選一**（少一次呼叫；但會改變表單的既有行為與用量歸類，需要重跑 #164 與本評測）。
   - b. 保留兩次呼叫，但在表單選擇提示中列出可提議的案件類型名稱，並明說「符合這些案件類型的請求不要給表單」（改動較小；同樣要重跑兩份評測）。
   - c. 先重跑一次 `eval-form-requests`，確認表單層這次對知識問題給表單是不是模型行為改變；若是，表單提示本身也需要收緊。
2. **案件選擇提示補上邊界**（不論採用哪種做法都建議）：在 `CaseProposalRules.SelectionPrompt` 加入「詢問既有案件或申請的進度、取消已送出的申請、統計數字、只是抱怨或陳述而沒有要求處理時，不要呼叫」；並把「只有符合某個類型的說明才呼叫，作物病蟲害等不屬於任何類型的事不要套用最接近的類型」寫明。這可以降低 n04、a03、a07、q03 與表單題的案件層誤觸。
3. **類型說明的寫法**：管理者寫類型說明時，建議同時寫「包括什麼」與「不包括什麼」（例如「設備報修：…不包括作物病蟲害，請用田間異常回報」）。設定頁的說明欄可加這個提示（前端小改，非必要）。
4. **關鍵字模式**（`Keyword` 觸發的部署才受影響）：
   - 類型名稱本身含開案關鍵字是常態（本題庫三個都是），問類型規則的題目會被誤觸。建議在 `CaseProposalRules.AsksForCase`／`KeywordProposal` 加一個「問句排除」：問題含「？」「嗎」「多久」「流程」「規定」「進度」「哪些」「怎麼」「可以」時不提議。以本題庫模擬，案件層誤觸 7 → 0、命中 3 → 3（不影響已命中的題目）；但「要怎麼申請？」這類真正想開案的問法也會被排除，且題庫是為了找弱點寫的，有過度擬合的風險，是否採用請負責人決定。
   - 關鍵字的漏觸（13/16）沒有好的修法：補同義詞會像 #164 一樣帶來新的誤觸。需要提議開案的部署應使用 `Model` 觸發（並先完成第 1 點）。
5. **模型呼叫成本可接受**：案件選擇每次約 650／70 token；正式環境只有表單沒有成立、且不是統計問題時才呼叫。
6. 上線後以實際對話抽樣再評一次（特別是「問進度」「取消」這兩類）。
