# ADR｜後端里程碑順序：先打通「文件 → 檢索 → 有引用的回答」

**狀態：** 已確認（2026-09-25）

## 決策

後端依以下順序建置，取代交接文件（`docs/handoff/ai-assistant-backend-integration-handoff.md`）建議的「知識庫 → 數據庫 → 發布 → 對話」：

1. **骨架**：登入、組織隔離、OpenAPI 產生前端型別、CI。
2. **知識庫**：上傳、背景處理、切段與向量、檢索。
3. **平台內對話**：只開放組織內部使用，含查無結果門檻與引用驗證。
4. **數據庫**：表單紀錄、撤回、固定查詢工具、趨勢與定期報表。
5. **對外發布**：網站嵌入（網域白名單）與 LINE。

## 理由

專案最大的風險是 AI 能否正確回答並引用；照交接文件順序要到最後才驗證得到。發布管道放最後，因為它依賴對話，且對外開放前需先有防濫用與嵌入網域限制。

## 補充（2026-09-26）

[業務流程審查](../reviews/2026-09-26-project-review-and-backlog.md)提出的「跨部門案件、交接與追蹤」（待補功能 6）排在數據庫里程碑之後：案件需要表單與受控的結構化紀錄，也需要平台內對話把問題轉成案件。開工前先另寫 ADR，定義文件、表單與工作項目三者的關係。它與對外發布的先後已由負責人決定：對外發布（M5）在前，案件排在 M7（2026-10-06 修正，原寫「在那份 ADR 中決定」，見補充（2026-10-06））。

## 補充（2026-09-27）

審查「待補功能 5」中 M3 沒有涵蓋的部分，另成一個「助理驗收與維護」里程碑，排在平台內對話之後，**必須在對外發布之前完成**，作為對外發布的閘門。範圍包括：

- 每個助理可保存的測試題組，以及「全部重跑」；
- 答錯或查無資料時建立處理事項並指派負責人，包含「問題未解決時轉人工」；
- 文件改版或權限變更後，重跑受影響助理的題組；
- 營運追蹤清單（查無資料、錯誤引用、處理人與重驗時間），且不揭露私人對話內容。

這些都以 M3 的真實對話與不含內容的指標為基礎（見 [M3 計畫](../plans/2026-09-27-backend-milestone-3-in-platform-chat.md) 第 7 節決定 E）。「處理事項」與待補功能 6 的「工作項目」可能是同一個概念，兩者的關係在待補功能 6 的 ADR 中一併定義；這個里程碑與數據庫里程碑的先後，在它的計畫中決定。

## 補充（2026-09-29）

「助理驗收與維護」訂名為 **M3.5**，排在 M4 數據庫之前（負責人 2026-09-29 決定）。計畫見 [M3.5 計畫](../plans/2026-09-29-assistant-acceptance-milestone.md)。
