## 1. 目的

#286 留下一個問題：助理有可提議的案件類型、但沒有接表單時，作物病蟲害的題目（f01–f06）6/6 被提議成案件，其中 5 題是「設備報修」、1 題是「採購申請」。

負責人決定先試不改程式的作法：由管理者在類型說明同時寫「包括什麼」與「不包括什麼」（#257 報告第 4 節建議 3）。本票量測這個作法有沒有效。

## 2. 方法

- **評測 CLI**：`eval-case-proposals` 新增 `--types <檔案>`。
  - 同一份題庫可以換一組類型名稱與說明。檔案的 `caseTypes` key 與順序必須和題庫相同，這樣標記與固定的類型 id 才會指向同一個類型。
  - 說明長度上限沿用正式環境的 500 字。
  - 不加這個參數時，用題庫內建的說明，行為與之前相同。
  - 報告會寫出用的是哪個類型說明檔，以及它的指紋。
- **新的一組說明**（`types-with-exclusions.json`）：三個類型都先寫範圍與「包括」，再寫「不包括」，並說明排除的事情該走哪裡。長度約 100–120 字，原本是 26–33 字。

  | 類型 | 說明 |
  | --- | --- |
  | 設備報修 | 農機、灌溉、溫室、冷藏庫、感測器等設備故障或損壞，需要派人到場檢查或維修。包括機器不能運轉、管線漏水、溫控或電控失靈。**不包括作物病蟲害、作物生長異常，例如葉子變色、枯萎、長蟲，這些請用田間異常回報**，由技術人員追蹤。 |
  | 採購申請 | 向廠商購買肥料、農藥、種苗、包材等資材或設備，需要主管核准後才能下單。包括庫存不足要補貨、要添購新的工具或機器。**不包括設備壞了要修理，請用設備報修；也不包括客戶向我們訂貨。發現病蟲害時請先做田間異常回報**，由技術人員判斷要不要用藥，再提採購。 |
  | 客戶退貨 | 客戶收到我們出貨的農產品有品質問題、數量不符或寄錯，要求退貨、換貨或退款。包括商品損壞、變質、少件或重量不足。**不包括客戶只是反映意見、沒有要求退換或退款**，這類請直接回覆客戶；也不包括我們把資材退回給供應商。 |

  - 採購申請也寫了「發現病蟲害時先回報」，因為 #286 的 f04（登記蚜蟲）被提議成採購申請。這是農場常見的用藥流程，不是題庫的題目清單。
  - 客戶退貨寫的「只是反映意見」會影響模糊題 a03（客戶抱怨芒果太酸）。
- **其他條件與 #286 完全相同**：
  - 正式環境的工具定義與提示（`CaseProposalRules`、`ProposalSelectionRules`）都沒有改。
  - 模型、題庫、範例表單（田間異常回報）也相同。
  - 類型說明會放進 `propose_case` 工具的說明，「案件層」與「整條提議階段」兩種呼叫都會用到。

## 4. 結論

- **主要問題沒有改善**：沒有表單時，作物病蟲害仍然 6/6 被提議成案件。
  - 寫進「設備報修」的「不包括作物病蟲害」沒有讓模型放棄提議，反而讓 f04 也移到設備報修。
  - #286 也是同樣的情況：提示裡的「不屬於任何類型的事（例如作物病蟲害），不要套用最接近的類型」沒有效果。
  - 這表示問題不在類型說明寫得清不清楚。只提供 `propose_case` 一個工具時，模型對「需要有人處理的事」傾向一定要呼叫，然後挑一個類型。類型說明只影響挑哪一個，不影響要不要呼叫。
- **沒有副作用**：應提議的 16 題，在兩種路徑都 0 漏觸、0 選錯類型；整條提議階段的 50 題結果與 #286 完全相同。
- **案件層的其他誤觸**：一題變好（a03），兩題變差（n02、a07）。只跑一次，不能下結論。
- **成本**：每次選擇呼叫多約 222 個輸入 token。
- **文件**：因為對要解決的問題無效，本票**沒有**把「寫明不包括什麼」當成建議寫進管理者文件（`deploy/README.md` 等）。管理者仍可以這樣寫，作用是幫助組織內的人分辨類型，但不能指望它擋住助理的誤提議。

## 5. 下一步選項（請負責人決定）

1. **讓案件呼叫有明確的「都不符合」選項**，需要改正式程式並重跑本評測。
   - 例如在 `caseTypeId` 的列舉加一個 `none` 值，或另外提供一個 `no_matching_case_type` 工具，讓模型在只有案件工具時也有地方表達「不符合」。
   - 有表單時，模型有第二個工具可選，f01–f06 就 6/6 給了表單。這是目前最直接的證據，說明「有另一個選項」才是有效的作法。
2. **助理有可提議的類型、但沒有連接任何表單時，設定頁提醒管理者**。例如作物或田間異常要用表單接，否則可能被提議成案件。這是產品與前端的改動，不改模型呼叫。
3. **提議後的伺服器端二次確認**：模型提議後，再呼叫一次模型，只問「這件事是否屬於〈類型〉：〈說明〉」，回答「否」就不提議。每題多一次呼叫，約 +700 個輸入 token。
4. **繼續改提示**，例如要求模型先引用說明中符合的「包括」項目再呼叫。#286 的邊界與本次的說明都沒有效果，這個方向的預期效果較低。
5. **任何選項都建議先量變異**：同一組設定重跑 3 次，再判斷 n02、a07、a05 的變化是不是雜訊。本票照指示只跑一次。

本票照指示沒有為了數字調整題庫或題目，也沒有改正式的提示或程式行為。
